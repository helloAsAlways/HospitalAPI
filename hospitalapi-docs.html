HospitalAPI

A RESTful backend for managing a hospital's people and clinical workflow — patients, doctors, nurses, appointments, diagnoses, treatment plans, medical records and schedules — built on ASP.NET Core and Entity Framework Core over a PostgreSQL database.

.NET 9.0 EF Core 9 PostgreSQL / Supabase Npgsql OpenAPI 9 entities · 8 controllers
View repository on GitHub →

01 Overview

What the project is and the problem it models.

HospitalAPI is a Web API (no UI) that exposes CRUD endpoints for the core records a hospital keeps. The domain is organised around a single Person record that each Patient, Doctor and Nurse extends by sharing its primary key, so one human is stored once and can play a clinical role without duplicating name, date of birth or contact details.

On top of those people sit the clinical events: a Patient books an Appointment with a Doctor; an appointment may produce one Diagnosis; a diagnosis may lead to one or more TreatmentPlans. Doctors publish availability as Schedules, and either party can attach free-text MedicalRecords. The solution folder is named HospitalAPI, but the .NET project inside it still carries the template name WebApplication2 — that name appears in namespaces and the .csproj.

PATTERN

Shared-key subtypes

Patient / Doctor / Nurse each own a 1:1 identifying relationship with Person via a shared PersonId.

STYLE

Thin controllers

Controllers talk straight to the EF Core DbContext. No service or repository layer sits in between.

STORAGE

Postgres, snake_case

Entities map to existing snake_case tables through UseSnakeCaseNamingConvention().

03 Architecture

How a request travels through the app.

The app is deliberately flat. A request hits a controller action, which uses the injected MyAppContext (the EF Core DbContext) to read or write, and EF translates that to SQL against PostgreSQL. There is no separate business or data-access layer — the controller is the handler.

// Program.cs — the whole pipeline
HTTP request
   │
   ▼  Routing            // [Route("api/[controller]")]
Controller action        // e.g. AppointmentsController.BookAppointment()
   │
   ▼  MyAppContext        // injected DbContext (Scoped)
Entity Framework Core    // LINQ → SQL, change tracking, SaveChangesAsync()
   │
   ▼  Npgsql
PostgreSQL (Supabase)    // snake_case tables

The Person shared-key pattern

This is the one idea worth understanding before reading the code. Patient, Doctor and Nurse do not have their own identity — they reuse Person.Id as their own primary key and as the foreign key back to Person. Because PersonId matches neither EF's Id nor <Type>Id convention, each of those classes needs an explicit [Key] attribute. Creating a patient therefore inserts a Person and a Patient row together in one SaveChangesAsync():

// PatientsController.CreatePatient — Person + Patient in one transaction
var person = new Person { Name = req.Name, DateOfBirth = req.DateOfBirth, ... };
var patient = new Patient { Person = person, MedicalHistoryNotes = req.Notes };
_context.Patient.Add(patient);          // EF inserts Person first,
await _context.SaveChangesAsync();      // then wires the shared PersonId

A consequence you can see in the endpoints: the {id} for a patient, doctor or nurse is the PersonId, and their PUT actions only edit role-specific fields (a patient's notes, a doctor's speciality). Editing a shared field like Name would belong on a Person-level action, which the project does not currently expose.

04 Data model & UML

Nine entities and the relationships EF Core configures between them.

Relationships & delete behaviour

All relationships and their on-delete rules are declared in MyAppContext.OnModelCreating. The delete rules are intentional, not defaults:

FromToCardinalityOn deleteMeaning
PersonPatient / Doctor / Nurse1 : 1—Identifying; role shares Person.Id.
PatientAppointment1 : 0..*CascadeRemoving a patient removes their appointments.
DoctorAppointment1 : 0..*SetNullRemoving a doctor keeps the appointment (doctor cleared).
Patient / DoctorMedicalRecord1 : 0..*DefaultRecords reference both participants.
DoctorSchedule1 : 0..*CascadeRemoving a doctor removes their availability.
AppointmentDiagnosis1 : 0..1CascadeOne diagnosis per appointment (unique FK).
DiagnosisTreatmentPlan1 : 0..*CascadePlans belong to a diagnosis.
Enum storage. Appointment.Status (Pending / Booked / Cancelled / Completed) is persisted as a lowercase string through a value converter rather than as an integer, so the column stays human-readable.

06 Setup

Get the API running locally.

Prerequisites

SDK

.NET 9 SDK

Install from the official .NET downloads. Verify with dotnet --version.

DATABASE

A PostgreSQL instance

A Supabase project (or any Postgres) with the hospital tables created.

OPTIONAL

An HTTP client

The bundled .http file, curl, Postman, or Swagger UI.

1 — Clone

git clone https://github.com/helloAsAlways/HospitalAPI.git
cd HospitalAPI

2 — Configure the database connection

Program.cs reads the connection string from a DBCONNECTION environment variable, so the cleanest option is to set it there. For local development the project uses Properties/launchSettings.json; replace the placeholders with your own Supabase credentials:

// launchSettings.json → profiles → http → environmentVariables
"DBCONNECTION": "Host=<your-host>.pooler.supabase.com;Port=6543;
              Database=postgres;Username=<your-user>;
              Password=<your-password>;SSL Mode=Require;
              Trust Server Certificate=true"

3 — Restore & run

dotnet restore
dotnet run

The API listens on the ports from launchSettings.json:

ProfileBase URL
httphttp://localhost:5110
httpshttps://localhost:7299
On the schema. There are no EF Core migrations in the repo — the entities map onto existing snake_case tables. Make sure your Postgres already has persons, patients, doctors, appointments and the rest before calling the API, or add migrations with dotnet ef migrations add Init.

08 Usage examples

A minimal end-to-end flow: create a doctor, then a patient, then book them together.

Create a doctor

curl -X POST http://localhost:5110/api/Doctor \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Dr. John Siddique",
    "dateOfBirth": "1985-05-15",
    "contactNumber": "+60-12-345-6789",
    "speciality": "Cardiology"
  }'

# 201 Created → returns the doctor, whose personId is the new id

Create a patient

curl -X POST http://localhost:5110/api/Patients \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Amir Hakim",
    "dateOfBirth": "1998-11-02",
    "contactNumber": "+60-11-222-3333",
    "medicalHistoryNotes": "No known allergies"
  }'

Book an appointment

Use the two personId values returned above. The server checks both exist, then stamps the appointment as booked:

curl -X POST http://localhost:5110/api/Appointments \
  -H "Content-Type: application/json" \
  -d '{
    "patientId": 12,
    "doctorId": 7,
    "scheduledTime": "2026-08-01T09:30:00Z"
  }'

# 400 Bad Request if patientId or doctorId does not exist

Cancel it

curl -X PATCH http://localhost:5110/api/Appointments/1/cancel
# 204 No Content — status is now "cancelled"
Tip. The repo includes WebApplication2.http, which runs these calls directly from Visual Studio or VS Code (with the REST Client extension) without needing curl.

09 Notes & caveats

Known rough edges worth addressing before this goes anywhere near real use.

1 · Unused packages. The .csproj references the SQL Server EF provider, Dapper and the Supabase client libraries, but the code only uses Npgsql + EF Core. Trimming them shrinks the dependency surface and removes ambiguity about which database the project targets.
2 · Inconsistent route naming. Every resource is plural (/api/Patients, /api/Nurses) except doctors (/api/Doctor). Renaming the controller to DoctorsController would make the surface predictable.
3 · No migrations, no auth. There are no EF Core migrations (entities assume the tables already exist) and no authentication or authorization on any endpoint — anyone who can reach the API can read and write patient data. Both are expected for a course project, but both are blockers for real deployment of anything holding medical records.
4 · OpenAPI is mapped outside Development. In Program.cs, app.MapOpenApi() runs only when the environment is not Development — the reverse of the usual setup — so the generated spec is exposed in production rather than locally. Worth double-checking that's intended.
